# Story 1.2: Frontend Navigation Shell

Status: ready-for-dev

## Story

As a user,
I want a persistent navigation structure to access the Clientes and Contactos sections of the application,
so that I can move between sections without full page reloads from any device.

## Acceptance Criteria

1. **Given** the application is loaded on a desktop browser (viewport ≥1024px / Tailwind `lg` breakpoint), **When** the user views the app, **Then** a `NavigationRail` (siesa-ui-kit) is visible with "Clientes" and "Contactos" entries, **And** clicking either entry navigates to `/clientes` or `/contactos` via TanStack Router (`Link`/`navigate`) with no full page reload (FR28).

2. **Given** the application is loaded on a mobile browser viewport (<1024px), **When** the user views the app, **Then** a `NavigationBar` (siesa-ui-kit) is displayed instead of the rail, **And** all navigation items are accessible and tappable (adequate touch target, `aria-label` present) (FR29).

3. **Given** the user types `/clientes` or `/contactos` directly in the browser URL bar, **When** the page loads, **Then** the correct view renders directly with no redirection to a home/root screen (FR30).

4. **Given** the user navigates to `/` (root), **When** the page loads, **Then** the app redirects to `/clientes`.

5. **Given** the user navigates to an unknown route, **When** the page loads, **Then** a 404 / not-found view is displayed gracefully inside the app shell (navigation remains visible, no blank page, no unhandled JS error).

6. **Given** the NavigationRail (desktop) or NavigationBar (mobile) is rendered, **When** the current route is `/clientes` or `/contactos`, **Then** the corresponding nav item is visually marked as selected/active.

## Dev Notes

### 🎨 UI Implementation Requirements (MANDATORY)

- **Library**: `siesa-ui-kit` (already installed — see Story 1.1, version `1.0.256` in `frontend/package.json`)
- **Components**: `NavigationRail` (desktop) + `NavigationBar` (mobile) — native components, do NOT build custom nav UI
- **Icons**: Heroicons only (`@heroicons/react/24/outline`) — `lucide-react` is prohibited per the Story 1.1 code-review fix (it was removed from the project)
- **Responsive strategy**: Tailwind CSS at the `lg: 1024px` breakpoint — the critical breakpoint per `architecture.md` §Cross-Cutting Concerns. Do not implement the rail/bar swap with JS media-query listeners.

### siesa-ui-kit component contracts (verified against the installed package)

```typescript
// NavigationRail.types.d.ts
interface NavigationRailItemProps {
  icon: ReactNode; label: string; selected?: boolean; disabled?: boolean;
  badge?: boolean; badgeCount?: number; onClick?: () => void; ariaLabel?: string; id?: string;
}
interface NavigationRailProps {
  items: NavigationRailItemProps[];
  alignment?: 'top' | 'center' | 'bottom'; // default 'top'
  selectedId?: string;
  onItemSelect?: (id: string) => void;
  className?: string;
}

// NavigationBar.types.d.ts
interface NavigationBarItem {
  id: string; icon: ReactNode; label: string; active?: boolean; disabled?: boolean;
  onClick?: (id: string) => void; ariaLabel?: string;
}
interface NavigationBarProps {
  items: NavigationBarItem[]; // max 5 recommended
  activeItemId?: string;
  onItemClick?: (id: string) => void;
  className?: string; ariaLabel?: string; // default 'Navigation Bar'
}
```

Note the prop-name asymmetry: `NavigationRail` uses `selectedId` / `onItemSelect` / `selected`, `NavigationBar` uses `activeItemId` / `onItemClick` / `active`. Map both from the same shared nav-items array plus a single `useMatchRoute()` result — don't duplicate route-matching logic per component.

`LayoutBase` (`siesa-ui-kit/dist/views/LayoutBase`) is also available and wraps a full Navbar + `NavigationRailGroup` sidebar (branding, user dropdown) — it is heavier and more opinionated than this story's AC require. Using the standalone `NavigationRail`/`NavigationBar` components directly (as the epic and test-design doc specify) is sufficient. If `LayoutBase` is adopted instead, note its `navigationItems` prop expects `NavigationRailGroupMenuItem[]`, not `NavigationRailItemProps[]` — do not mix the two shapes.

### Routing patterns (TanStack Router file-based, v1.170, already configured in `vite.config.ts`)

- Prefixes (company standard): `_` = pathless layout (no URL segment), `$` = dynamic param, `-` = ignored/colocated file.
- `_app.tsx` + `_app/clientes.tsx` + `_app/contactos.tsx` produces `/clientes` and `/contactos` sharing the `_app` layout without an extra URL segment — matches `architecture.md`'s documented tree (`routes/_app.tsx`, `routes/_app/clientes.tsx`, `routes/_app/contactos.tsx`).
- 404 handling: use the root route's `notFoundComponent` option (`createRootRoute({ notFoundComponent: NotFoundView })`) rather than a catch-all `$` file route, so the shell/nav layout stays mounted for unmatched paths.
- Root redirect: `createFileRoute('/')({ beforeLoad: () => { throw redirect({ to: '/clientes' }) } })`.
- Navigation must use `useNavigate()` / `<Link>` from `@tanstack/react-router` — never `window.location.href` or `.reload()`. This is what makes navigation reload-free (FR28) and is what TC-E1-P1-01 asserts.

### Scope boundary (per `epic-01-foundation.md`)

This story only builds the navigation shell and placeholder route views. Full Clientes/Contactos CRUD screens (list, detail, forms) are Epic 2 and Epic 3 scope — do not implement `ClienteListView`/`ContactoListView` business logic here, only enough placeholder content (heading + `EmptyState`) to prove the route resolves correctly.

### Previous Story Intelligence (Story 1.1)

- Package manager is `pnpm` — use `pnpm add` / `pnpm run`, not npm/yarn.
- Icon standard enforced via Story 1.1 code review: `@heroicons/react` only; `lucide-react` was removed from the project — do not reintroduce it.
- `frontend/src/shared/components/ui/` holds shadcn-sourced components (`dialog.tsx`, `breadcrumb.tsx`); this story's new components (`AppNavigation.tsx`, `NotFoundView.tsx`) are siesa-ui-kit-based, not shadcn — place them directly under `frontend/src/shared/components/`.
- `frontend/src/routes/__root.tsx` currently just wraps `<Outlet />` in a `min-h-svh` div (see current implementation) — extend it (add `notFoundComponent`), don't remove its existing structure.
- No Vitest test environment is configured yet anywhere in the project (`frontend/vite.config.ts` has no `test` block, no `test` script in `package.json`) — this is the first story requiring component tests, so Task 4 is a prerequisite, not optional.
