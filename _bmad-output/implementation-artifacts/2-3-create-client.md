# Story 2.3: Create Client

Status: done

## Story

As a commercial team member,
I want to register a new client by filling in a form,
so that the client is available in the system immediately for the whole team.

## Acceptance Criteria

1. **Given** the user is on the `/clientes` view, **When** the user clicks "Nuevo cliente" (`data-testid`-free — matched by accessible role/name per `e2e/pages/clientes.page.ts`'s `btnNuevoCliente = getByRole('button', { name: /nuevo cliente/i })`), **Then** a modal dialog (`role="dialog"`, matched by `clientesPage.form`) opens with four fields — Nombre, NIT/RUC, Teléfono, Ciudad — each with an accessible `<label>` (via siesa-ui-kit `Input`'s `label` prop, matched by `page.getByLabel(/nombre|nit|teléfono|ciudad/i)`), all required (FR1).

2. **Given** the dialog is open and the user fills all four required fields with valid data, **When** the user clicks "Guardar" (`role="button"`, name `/guardar/i`), **Then** `POST /api/v1/clientes` is called, the new client appears in the client list immediately with no page reload (FR27 — via `queryClient.invalidateQueries({ queryKey: ['clientes'] })`), a success toast shows the exact Spanish copy **"Cliente creado correctamente"**, and the dialog closes.

3. **Given** the dialog is open, **When** the user clicks "Guardar" with one or more required fields empty, **Then** clear inline error messages appear next to each empty field (via siesa-ui-kit `Input`'s `error`/`errorMessage` props, rendered text matching `/requerido/i`) (FR8), **no** `POST` request is ever sent (client-side Zod validation blocks submission), and the dialog remains open.

4. **Given** the dialog is open and the user submits a NIT/RUC that already exists in the system, **When** the backend responds `409 Conflict`, **Then** an inline error message **"El NIT/RUC ya está registrado"** appears next to the NIT/RUC field (matches `e2e`'s `/nit.*ya existe|ya.*registrado/i`) without exposing any technical/exception detail (NFR6), the dialog remains open (not closed), and the user can correct the NIT and resubmit.

## Dev Notes

### Architecture patterns and constraints

- **No pre-check `ExistsByNitAsync`, DB constraint is the single source of truth**: rather than adding a separate "check if NIT exists" repository call before insert (which would still have a race window under concurrent requests), `AddAsync` attempts the insert directly and translates a `uk_clientes_nit` unique-violation into `false`. This is both **simpler** (one repository method, not two) and **more correct** (TC-E2-P0-06 requires the invariant to hold even under concurrent/bypassing-frontend requests — only the database constraint, not an app-level pre-check, can guarantee that).
- **Expected outcomes are return values, not exceptions** (same pattern Story 2.2 established for `GetByIdAsync` returning `null` on 404): a duplicate NIT is a normal, anticipated business outcome of "create a client", not a system failure — modeled as `CreateClienteResult.IsConflict`, decided by the endpoint, not a new custom exception type or exception-handling middleware branch. The existing `ExceptionHandlingMiddleware` (Story 1.3) is untouched and still correctly turns genuine unexpected failures into safe `500`s.
- **Client-side and server-side validation are two independent layers** (NFR5, `architecture.md`'s "Validation: Both sides"): Zod (`clienteSchema.ts`) blocks empty-field submission before any network call (AC #3's "no POST fires" requirement); `CreateClienteRequestValidator` (FluentValidation) re-validates server-side and returns `400` regardless of what the frontend sent — this is defense-in-depth, not duplicated business logic, since a future non-browser client (script, mobile app) could otherwise bypass Zod entirely (exactly TC-E2-P0-06's reasoning, applied to required-field validation too).
- **Mutation pattern**: `useCreateCliente` follows `architecture.md`'s canonical snippet verbatim — `onSuccess` invalidates `['clientes']` (triggers `ClienteListView`'s `useClientes()` refetch, satisfying FR27 "changes immediately visible") then shows the success toast. The `409`-vs-other-failure branching intentionally lives in `ClienteForm`'s `onSubmit` (via `mutateAsync` + `try/catch`), not in the hook's `onError`, because the two failure modes need different UI treatment (inline field error vs. generic message) and the hook itself has no knowledge of which RHF field to attach an error to.
- **`siesa-ui-kit` `Input` is the correct component for inline validation errors**: its `label`/`error`/`errorMessage` props render an accessible `<label htmlFor>` plus a conditional error paragraph with zero extra markup — confirmed by reading the installed package's embedded source (`Input.tsx`, via its `.js.map`'s `sourcesContent`). No custom form-field wrapper component is needed.
- **This is a Dialog form, not MasterCrud**: per `mastercrud-use-reference.md` (mandatory reference for any CRUD/form-based UI) and Story 2.1's already-established decision, `MasterCrud` is a paginated-table + form orchestrator for a different UX shape entirely (server-side pagination, generic `CrudService<T>` contract, company-scoping). `/clientes` is a custom split-panel with instant client-side search and a single simple 4-field create form — none of `MasterCrud`'s value (pagination, lookups, multi-company) applies here, and forcing it in would mean building an adapter around a component whose contract (`getAll`/`getById`/`create`/`update`/`delete` all taking a `company` param, paged `GetAllResponse<T>`) doesn't match this app's plain-array API responses. A plain `Dialog` + React Hook Form + Zod is the minimal-complexity, architecture-documented shape (`ClienteForm.tsx` is explicitly named in `architecture.md`'s directory tree).
- **`architecture.md`'s REST table lists `POST /api/v1/clientes → Create`** with response shape `201 Created + created object` (Format Patterns section) — implemented via `Results.Created($"/api/v1/clientes/{id}", dto)`, consistent with the already-existing `GET /api/v1/clientes/{id:guid}` (Story 2.2) that the `Location` header points to.
