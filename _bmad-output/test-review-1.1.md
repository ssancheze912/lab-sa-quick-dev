## Recommendations (Should Fix)

### 1. Add Formal Test IDs to Aid Traceability

**Severity**: P2 (Medium)
**Location**: All 4 test files (test titles)
**Criterion**: Test IDs / Traceability
**Knowledge Base**: `traceability.md`, `test-quality.md`

**Issue Description**:
Tests are identified only by descriptive titles. Adding formal IDs (e.g., `1.1-E2E-001`, `1.1-API-005`) would enable exact matching in the traceability matrix generated by `testarch-trace` and make it trivial to reference a specific test in gate decisions, defect reports, or PR discussions.

**Current Code**:
```typescript
test('should serve the frontend app on port 5173 without errors', async ({ page }) => { ... });
```

**Recommended Improvement**:
```typescript
test('1.1-E2E-001 — should serve the frontend app on port 5173 without errors', async ({ page }) => { ... });
```

**Benefits**: Cleaner mapping in `traceability-1.1.md`, faster PR triage, easier grep by ID.
**Priority Rationale**: P2 because current descriptive titles are already unambiguous; IDs are a "nice to have" for large suites.

---

### 2. Add `[P0]` Priority Tags to ATDD Baseline Tests

**Severity**: P2 (Medium)
**Location**: `project-initialization.spec.ts`, `backend-initialization.api.spec.ts`
**Criterion**: Priority Markers
**Knowledge Base**: `test-priorities.md`

**Issue Description**:
Edge tests correctly tag priority (`[P1]`, `[P2]`, `[P3]`) in test titles, but the ATDD baseline tests — which are implicit P0 (blocking the release) — carry no explicit marker. This makes it harder for CI/CD to filter runs by priority.

**Current Code**:
```typescript
test('should have the backend API server running on port 5000', async ({ request }) => { ... });
```

**Recommended Improvement**:
```typescript
test('[P0] should have the backend API server running on port 5000', async ({ request }) => { ... });
```

**Benefits**: Uniform priority tagging across all test files enables tag-based selective test execution.
**Priority Rationale**: P2 because baseline tests are executed in every CI run regardless.

---

### 3. Consider Extracting Common Setup into Fixtures

**Severity**: P3 (Low)
**Location**: All 4 files
**Criterion**: Fixture Patterns / DRY
**Knowledge Base**: `fixture-architecture.md`

**Issue Description**:
The `API_BASE_URL` constant and console-error listener registration is repeated across files. A shared fixture in `e2e/fixtures/` would centralize this setup.

**Recommended Improvement**:
```typescript
// e2e/fixtures/env.ts
export const test = base.extend<{ apiBaseURL: string }>({
  apiBaseURL: async ({}, use) => {
    await use(process.env.API_BASE_URL ?? 'http://localhost:5000');
  },
});
```

**Benefits**: Single source of truth for environment configuration; easier to add new fixtures (e.g., `errorCollector`).
**Priority Rationale**: P3 — infrastructure smoke tests are small and duplication is minimal; defer until domain tests need fixtures.

## Best Practices Found

### 1. Network-First Pattern (Excellent)

**Location**: `project-initialization.spec.ts:28-32`, `project-initialization.edge.spec.ts:91-101`
**Pattern**: Register response listener BEFORE navigation
**Knowledge Base**: `network-first.md`

```typescript
// ✅ Excellent pattern — listener registered BEFORE goto
const rootResponse = page.waitForResponse(
  (resp) => resp.url() === 'http://localhost:5173/' && resp.status() === 200
);
await page.goto('/');
const response = await rootResponse;
```

**Use as Reference**: This pattern prevents the classic race condition where the response arrives before the listener is attached. Apply the same pattern to any test asserting on network activity.

---

### 2. Resilient `data-testid` Selectors

**Location**: `project-initialization.spec.ts:46`, `project-initialization.edge.spec.ts:47, 142`
**Pattern**: `data-testid` attribute over CSS class or text selectors
**Knowledge Base**: `selector-resilience.md`

```typescript
await expect(page.locator('[data-testid="app-root"]')).toBeVisible();
```

**Use as Reference**: `data-testid` is the recommended selector — decoupled from styling changes, refactors, and i18n.

---

### 3. Security-Aware Negative Assertions

**Location**: `backend-initialization.edge.api.spec.ts:71-85, 166-185`
**Pattern**: Validate what should NOT happen (CORS foreign origins, no stack trace leaks)
**Knowledge Base**: `test-quality.md`

```typescript
// Reject wildcard AND echoed evil origin — no false positives
expect(allow).not.toBe('*');
expect(allow).not.toBe('http://evil.example.com');
```

**Use as Reference**: Combining positive and negative assertions in security-sensitive checks catches misconfiguration that positive-only tests would miss.
